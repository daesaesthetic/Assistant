# Phase 1.4B1 — Shared Groq Reliability Layer

You are implementing **Phase 1.4B1 — Shared Groq Reliability Layer** for Assistant-Beta-2.5.

The Phase 1.4B read-only audit has been completed and reviewed.

This is now an **implementation task**.

## Objective

Create a small, centralized reliability boundary around Groq requests that provides:

* Explicit request timeouts
* Controlled retry behavior
* Error classification
* Rate-limit awareness
* Safe structured logging

The goal is to make AI requests predictable and diagnosable without redesigning the assistant.

# 1. Shared Reliability Boundary

Create or extend the shared Groq utility so callers can make requests through one consistent reliability layer.

The abstraction should support the existing request types without forcing unrelated architectural changes.

It should be possible for callers to specify, when necessary:

* Request type/category
* Timeout
* Model/request parameters
* Whether the request is eligible for retry

Avoid exposing unnecessary implementation details to callers.

---

# 2. Explicit Timeout

Introduce application-level Groq timeouts.

Use these initial defaults unless repository inspection demonstrates a compelling reason to adjust them:

### Standard text requests

**30 seconds**

### Vision requests

**45 seconds**

### Background memory extraction

**15 seconds**

The timeout must apply to the actual Groq request.

Do not merely stop waiting in the Discord handler while leaving the underlying request uncontrolled.

Use the capabilities of the currently installed Groq SDK rather than adding another timeout dependency.

Make timeout values centralized/configurable inside the AI reliability layer.

---

# 3. Retry Policy

Implement a **single, explicit retry owner**.

Do not accidentally create:

```text
Application retry
    +
SDK retry
    +
Caller retry
```

which could multiply requests.

Determine the current SDK retry behavior and configure it explicitly so the application's intended retry policy is predictable.

### Recommended policy

At most **one application-visible retry** for transient failures.

Potentially retry:

* HTTP 408
* HTTP 409
* HTTP 500
* HTTP 502
* HTTP 503
* HTTP 504
* transient network/transport failures

Do NOT retry:

* HTTP 400
* Context-size failures
* malformed requests
* HTTP 401
* HTTP 403
* invalid model configuration
* malformed application data
* empty model responses

For HTTP 429:

* Inspect `Retry-After` when available.
* Retry only when the indicated delay is below a reasonable configured ceiling.
* Do not sleep for an excessive period inside a Discord interaction.
* If retrying would exceed the overall request deadline, fail cleanly instead.

Use short exponential backoff with jitter where appropriate.

Do not introduce a large retry framework for this.

---

# 4. Error Classification

Create a small internal error classification system.

Use these categories where applicable:

```text
configuration
rate_limit
context
transient_provider
network
timeout
empty_response
malformed_response
unknown
```

Do not over-engineer the taxonomy.

The classification must preserve the original error when useful for logging/debugging.

Callers should be able to determine the category without parsing raw error strings.

---

# 5. Rate-Limit Handling

When Groq returns HTTP 429:

1. Identify it as `rate_limit`.
2. Inspect available response headers safely.
3. Read `Retry-After` when present.
4. Determine whether a retry is reasonable.
5. Never retry indefinitely.
6. Never expose raw provider headers or internal errors to Discord users.

Log structured information such as:

* category
* HTTP status
* retry attempted
* retry delay if safe
* request type
* elapsed time

Do not log:

* API keys
* Authorization headers
* complete prompts
* complete model responses
* sensitive user content

---

# 6. Logging

Make AI failures observable.

Use the project's existing logging conventions where possible.

At minimum, reliability logs should identify:

* AI request category
* model
* error category
* HTTP status when available
* whether a retry occurred
* elapsed time
* timeout occurrence

Avoid introducing a large logging framework.

Do not dump complete exceptions if they may contain secrets or sensitive request data.

If the existing project uses `console.error`, structured prefixes/objects are acceptable.

---

# 7. Missing API Key

The current project creates a Groq client using a placeholder when `GROQ_API_KEY` is missing.

Do not redesign application startup in this task.

However, improve the reliability boundary so missing configuration is classified clearly as:

```text
configuration
```

rather than being treated as a generic provider failure.

Do not expose the key or raw authentication details.

# 11. Tests

Add or update tests only if the repository already has a testing structure suitable for them.

If adding tests is consistent with the existing project:
