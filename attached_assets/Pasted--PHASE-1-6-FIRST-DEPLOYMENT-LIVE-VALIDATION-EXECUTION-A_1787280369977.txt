## STEP 2 — SECRET CONFIGURATION
--------------------------------------------------

The bot requires these runtime secrets/configuration values:

- DISCORD_BOT_TOKEN
- DISCORD_CLIENT_ID
- GROQ_API_KEY

Potentially also:

- DISCORD_GUILD_ID

IMPORTANT SECURITY RULE:

NEVER ask the operator to paste tokens into chat.
NEVER print token values.
NEVER write tokens into source files.
NEVER write tokens into `.env` files that may be committed.
NEVER include secrets in logs or test output.

Instead, instruct the operator to add the values through the Replit Secrets/environment-variable interface.

When configuration is required, stop and explicitly ask the operator to configure:

DISCORD_BOT_TOKEN
DISCORD_CLIENT_ID
GROQ_API_KEY

If instant guild command registration is desired, also ask for:

DISCORD_GUILD_ID

The operator should only confirm that the secrets have been configured.

Do not request the actual secret values.

## STEP 8 — LIVE SMOKE TEST
--------------------------------------------------

After successful startup, perform controlled testing in the designated test server.

Test the highest-value functionality first.

### Core Discord tests

1. `/talk`
2. `/talk reset`
3. Normal follow-up conversation
4. Bot mention
5. Configured bot channel behavior

### AI tests

6. `/suggest`
7. `/suggest` with an image if supported
8. `/edit`
9. Memory extraction after a conversation
10. A follow-up that should benefit from conversation context

### Reliability tests

11. Send multiple messages rapidly enough to exercise the conversation queue.
12. Verify responses do not overwrite each other's conversation history.
13. Verify an invalid/failed AI response does not create fake history.
14. Verify a provider/configuration error produces a safe user-facing message.
15. Verify persistence degradation does not expose database internals.

### Discord behavior

16. Verify embeds/responses render correctly.
17. Verify messages remain within Discord's length constraints.
18. Verify command permissions behave as expected.
19. Verify automod/moderation functionality if included in the current release scope.

Do not intentionally abuse external APIs or spam requests.

Use a controlled test account/channel where possible.

--------------------------------------------------
## STEP 9 — MEMORY / CONTEXT VALIDATION
--------------------------------------------------

Perform a small realistic conversation test.

Example structure:

1. Tell the bot a harmless preference or fact.
2. Ask an unrelated question.
3. Later ask a question where that fact is relevant.
4. Verify the bot uses the information naturally.
5. Verify it does not mention databases, stored memories, memory extraction, or internal context.
6. Verify irrelevant memories do not dominate unrelated questions.

Also verify:

- Recent conversation takes precedence over older conflicting memory.
- Memory relevance behavior remains bounded.
- No fake memory is created from invalid AI responses.

Do not use sensitive personal information for testing.

## STEP 10 — FAILURE HANDLING
--------------------------------------------------

If live testing discovers a failure:

Classify it before changing code.

Categories:

- configuration
- Discord permissions
- command registration
- database initialization
- network/provider
- Groq
- Pollinations
- conversation concurrency
- context/memory
- response validation
- Discord delivery
- unrelated/pre-existing

Only implement a fix if:

1. The defect is real.
2. It affects first-release functionality.
3. The fix is small and directly related to deployment.
4. It does not unnecessarily expand project scope.

After every fix:

- Run affected tests.
- Run bot typecheck.
- Run workspace typecheck when appropriate.
- Re-run the failed live test.

Do not start a new architectural phase because of a minor cosmetic issue.
