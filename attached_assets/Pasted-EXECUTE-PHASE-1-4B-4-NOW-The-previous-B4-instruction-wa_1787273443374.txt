PHASE 1.4B.4 — MEMORY RELIABILITY
==================================================

B1, B2, and B3 are already implemented and committed.

Preserve them.

B4 ONLY addresses reliability, validation, bounds, persistence safety, and observability of the background memory-extraction pipeline.

Do NOT implement B5 or redesign the memory architecture.

--------------------------------------------------
1. PRIMARY RULE
--------------------------------------------------

Memory extraction is NON-CRITICAL.

A successful primary conversation response must remain successful if memory extraction:

- fails
- times out
- is rate limited
- returns malformed output
- returns invalid JSON
- returns invalid memory values
- fails during SQLite persistence

Memory extraction must never:

- throw into the primary conversation flow
- cause another primary Groq request
- change the primary response
- permanently block the B2 conversation queue

--------------------------------------------------
2. EXISTING GROQ RELIABILITY
--------------------------------------------------

Use the existing B1 shared Groq request boundary.

Do NOT create a raw/direct Groq request for memory extraction.

Preserve the existing memory-specific timeout, expected to be approximately 15 seconds unless the repository has a justified existing value.

Do not create a second retry system.

Do not stack SDK retries with application retries.

Use the existing B1 error categories where applicable:

- configuration
- rate_limit
- context
- transient_provider
- network
- timeout
- empty_response
- malformed_response
- unknown

Database failures should use:

- persistence

--------------------------------------------------
3. BACKGROUND EXECUTION
--------------------------------------------------

Memory extraction must remain background/best-effort.

The intended sequence is:

primary AI generation
→ conversation persistence
→ conversation queue releases
→ background memory extraction

A slow memory request must NOT hold the B2 per-conversation queue.

Do not introduce a global lock.

Do not make generateReply() wait for memory extraction.

--------------------------------------------------
4. MEMORY INPUT
--------------------------------------------------

Memory extraction may only run when B3 has produced a valid primary response.

Use:

- actual current user message
- actual valid assistant response

Do NOT run extraction after:

- empty primary response
- whitespace-only primary response
- malformed primary response
- failed primary AI generation

The old "..." placeholder must never be used as memory input.

--------------------------------------------------
5. OUTPUT CONTRACT
--------------------------------------------------

The expected memory extraction output is a JSON array of strings.

Valid example:

["The user likes cats.","The user is working on a Discord bot."]

Reject:

- invalid JSON
- JSON objects
- numbers
- booleans
- null
- nested objects
- nested arrays
- non-string array entries
- empty strings
- whitespace-only strings

Do not infer memories from arbitrary prose.

Do not build an elaborate natural-language parser.

If the existing parser supports Markdown JSON fences, preserve/support that behavior. Otherwise do not create a complicated parser solely for B4.

--------------------------------------------------
6. NORMALIZATION
--------------------------------------------------

Candidate memory strings must be:

- trimmed
- non-empty
- subject to a reasonable per-memory length limit

If there is no existing explicit application limit, use a conservative bound appropriate for one user fact.

Prefer REJECTING an overlong candidate rather than silently truncating it into a potentially corrupted fact.

Document the chosen limit.

Do not redesign the memory architecture.

--------------------------------------------------
7. MEMORY LIMIT

Preserve the existing maximum of approximately 30 memories per user/guild.

Do NOT:

- increase it
- remove it
- redesign retention
- add ranking
- add decay
- add semantic memory

If the existing database already enforces the limit, preserve that implementation.

Only fix a concurrency/cap issue if the current implementation demonstrably allows B4 to violate the existing limit.

Do not create a migration unless absolutely necessary.

--------------------------------------------------
8. DUPLICATES

- embeddings
- semantic similarity

- AI deduplication

Normalization must not accidentally bypass the existing duplicate protection.

--------------------------------------------------
9. MEMORY PERSISTENCE FAILURE
--------------------------------------------------

If:

primary AI succeeds
+
conversation persistence succeeds
+
memory persistence fails

then:

- primary response remains successful
- memory failure is logged
- failure is classified as persistence
- no database details reach Discord
- no primary AI request is repeated
- B2 queue remains unaffected

Memory persistence is best-effort.

Do not silently convert the primary response into a failure.

--------------------------------------------------

- credentials
- complete prompts

Keep logging concise.
