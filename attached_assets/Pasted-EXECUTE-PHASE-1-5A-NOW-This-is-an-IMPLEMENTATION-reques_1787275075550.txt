CURRENT PROBLEM
==================================================

The current conversation system combines:

- system instructions
- persona
- traits
- memories
- recent conversation history
- current message

into a provider request.

The existing approximate context budget is useful but not a sufficiently explicit architecture for future expansion.

Phase 1.5A must create a clear separation between:

1. Stable system instructions
2. Persona
3. Traits
4. Memory context
5. Conversation history
6. Current user message

==================================================
IMPLEMENTATION REQUIREMENTS
==================================================

Create or refactor a dedicated context-building boundary.

The conversation layer should be able to request something conceptually equivalent to:

buildConversationContext({
  botName,
  persona,
  traits,
  memories,
  history,
  currentMessage
})

and receive a validated model-message list or equivalent structured result.

The exact API is implementation-dependent.

The important requirement is architectural separation.

The context builder must own:

- section construction
- ordering
- context-size estimation
- history reduction
- memory/context bounds
- preservation of the current message

`generateReply()` should remain responsible for orchestration, not detailed context-budget logic.

==================================================
BUDGETING
==================================================

Replace the current informal budgeting behavior with an explicit, centralized budget policy.

Requirements:

- Preserve the current model.
- Preserve the current 800-token output limit unless the repository demonstrates a compelling reason otherwise.
- Reserve output capacity when calculating the input budget.
- Never remove the current user message.
- Prefer retaining recent conversation over older conversation.
- Never silently create an invalid message sequence.
- Avoid relying exclusively on `characters / 4` as if it were exact tokenization.

If an exact provider tokenizer is unavailable, use a clearly documented conservative estimator.

The implementation must expose the budget decision in a testable way.

Example conceptual result:

{
  messages,
  estimatedInputTokens,
  reservedOutputTokens,
  truncatedHistory,
  truncatedContext
}

The exact interface is up to the implementation.
