## OBJECTIVE

Improve the quality of conversation context by introducing deterministic relevance handling for optional user context, beginning with stored memories.

The goal is NOT to increase the context window.

The goal is to make the assistant select the most useful existing context before sending it to the model.

Current context construction already provides bounded sections and prioritizes recent conversation history. Preserve that architecture.

## CURRENT ARCHITECTURE

The primary conversation path is:

`generateReply()`
→ load bot name/persona/memories/traits/history
→ `buildConversationContext()`
→ `validateConversationContext()`
→ `createGroqCompletion()`

`conversation-context.ts` is the authoritative primary context builder.

It currently provides:

- Stable instructions.
- Persona.
- Traits.
- Memories.
- Recent history.
- Current message.
- Token estimation.
- Section budgets.
- Context truncation metadata.
- Final context validation.

Do not create a second context builder.

## REQUIRED SCOPE

### 1. Add memory relevance selection

Before memories are assembled into the final prompt, determine which stored memories are most relevant to the current user message.

The selection must be:

- Deterministic.
- Local.
- Fast.
- Explainable.
- Bounded.
- Free of additional AI/provider requests.

Do NOT call Groq to rank memories.

Do NOT introduce embeddings, vector databases, or new external services.

### 2. Preserve important memories

Relevance filtering must not simply discard memories because they do not share exact words with the current request.

The implementation should account for useful semantic-ish relationships using lightweight deterministic techniques appropriate for the current project.

If a reliable relevance strategy cannot be implemented without inventing semantics, STOP and report the limitation instead of pretending that keyword matching is semantic understanding.

### 3. Preserve current context guarantees

The existing priority model remains authoritative:

1. Current user message
2. Stable assistant instructions
3. Recent conversation
4. Persona
5. Traits
6. Relevant memories

Do not allow memory relevance logic to displace the current message or recent conversation.

### 4. Keep memory storage unchanged

Do NOT modify:

- Database schema.
- Memory tables.
- Memory extraction.
- Memory uniqueness rules.
- Existing 30-memory limit.
- Memory persistence behavior.

This phase is about READ-TIME SELECTION, not memory storage.

### 5. Preserve fallback behavior

If relevance scoring cannot identify useful memories:

- Do not fail the conversation.
- Fall back to the existing bounded memory behavior.
- The primary AI request must remain functional.

An empty memory collection must remain valid.

### 6. Keep context construction pure

The relevance calculation must not mutate:

- Stored memories.
- Conversation history.
- Persona.
- Traits.
- Current user input.

The context builder must remain a pure request-construction boundary.

### 7. Add safe metadata

Expose enough metadata to test/diagnose relevance behavior without logging user content.

Possible metadata:

- Total memories considered.
- Memories selected.
- Whether memory selection reduced the set.
- Whether the memory section was truncated.

Do NOT log:

- Memory text.
- User messages.
- Conversation history.
- Prompts.
- AI responses.

Do not add noisy logs for every normal request unless necessary.
