# B2 OBJECTIVE

Prevent concurrent conversation requests for the same user/guild context from silently overwriting each other's conversation history.

The current architecture performs a read-modify-generate-write sequence.

Conceptually:

```text
Request A:
    read history
    generate response
    write complete history

Request B:
    read history
    generate response
    write complete history
```

If A and B overlap, both can read the same old history.

Whichever request writes last can overwrite the other's conversation exchange.

This is the primary issue B2 must solve.

---

# REQUIRED BEHAVIOR

For a given:

```text
(userId, guildId)
```

conversation context:

### Requests must be serialized.

Example:

```text
Request A starts
Request B starts

A → read/generate/persist
A → complete

B → read/generate/persist
B → complete
```

B must not generate from the stale history that existed before A completed.

---

# IMPORTANT: DO NOT BLOCK DIFFERENT USERS

Serialization must be scoped to the conversation context.

For example:

```text
User A + Guild X
User B + Guild X
```

must be allowed to process concurrently.

Likewise:

```text
User A + Guild X
User A + Guild Y
```

should remain independent.

The locking/queue key should therefore correspond to the existing conversation scope, not simply the Discord user.

Use the repository's actual existing scope semantics as the source of truth.

---

# DEPLOYMENT ARCHITECTURE

Before choosing the concurrency mechanism, inspect the repository and deployment configuration.

Determine whether the current bot runs as:

* One process
* Multiple processes
* Multiple workers
* Horizontally scaled instances

If the current deployment is effectively a single bot process, an in-memory per-conversation queue/lock is likely the smallest appropriate solution.

If the repository demonstrates that multiple bot processes can simultaneously access the same SQLite database, do NOT blindly implement an in-memory lock.

In that case, evaluate whether optimistic/versioned persistence or another database-level mechanism is required.

Do not assume.

Document the conclusion.

---

# PREFERRED IMPLEMENTATION

Prefer the smallest solution that reliably protects the current architecture.

A likely single-process implementation would be a per-conversation asynchronous queue/lock:

```text
Map<conversationKey, Promise>
```

or an equivalent small utility.

The implementation must:

* serialize requests for one conversation
* allow unrelated conversations to run concurrently
* release the lock after success
* release the lock after failure
* release the lock after timeout
* avoid permanently orphaned locks
* avoid unbounded memory growth
* clean up idle conversation keys

Do not add a general-purpose queue framework.

Do not add a dependency unless absolutely necessary.

---

# CRITICAL: LOCK THE CORRECT BOUNDARY

Do not simply lock the final SQLite write.

That does NOT solve the stale-history problem.

The protected operation must cover the relevant read → generation → persistence sequence.

Conceptually:

```text
acquire conversation lock

    load current history
    build context
    call AI
    persist resulting history

release conversation lock
```

This ensures the second request reads the history produced by the first.

However, do not hold a database transaction open while waiting for Groq.

The lock should be application-level around the conversation workflow, while SQLite transactions remain short-lived.

# RESET SEMANTICS

This is a required part of B2.

Inspect how `/talk reset` currently works.

Determine what happens when:

```text
Request A is generating
Request B requests reset
```

Define deterministic behavior.

Preferred behavior:

```text
Existing request completes according to normal rules.

Reset waits for the current conversation operation.

Then reset clears the conversation.

Future requests see the reset state.
```

Do not allow a stale in-flight request to write history after reset has already cleared it.

If the current architecture requires a different safe solution, explain it before implementing.

# FAILURE SAFETY

The concurrency mechanism must be exception-safe.

Use a structure equivalent to:

```text
acquire

    execute conversation workflow
finally:
    release
```

Do not rely on individual success paths to release locks.

Every exit path must release the conversation context.

# PERFORMANCE REQUIREMENTS

The concurrency mechanism must not serialize the entire bot.

Bad:

```text
Global AI lock
    ↓
Only one AI request anywhere at a time
```

Good:

```text
User A / Guild X → locked
User B / Guild X → independent
User A / Guild Y → independent
```

Only requests targeting the same conversation context should wait.

Also ensure:

* idle locks are removed
* failed requests do not leak queue entries
* memory usage remains bounded
* no background polling loop is introduced
