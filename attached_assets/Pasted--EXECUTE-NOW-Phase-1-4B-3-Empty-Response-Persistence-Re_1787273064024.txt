# PART 1 — REMOVE FAKE EMPTY RESPONSES


---

# VALID RESPONSE DEFINITION

A primary AI response should only be considered valid if it contains usable textual content.

At minimum:

* response exists
* expected message content exists
* content is a string
* content remains non-empty after trimming

Do not over-engineer content validation.

Normal valid responses such as:

```text
"Sure."
```

must continue working.

Whitespace-only responses are invalid.

---

# EMPTY RESPONSE BEHAVIOR

When Groq successfully returns but produces no usable content:

1. Classify the result as an empty response.
2. Do not persist a user/assistant exchange containing a fake assistant response.
3. Do not invoke memory extraction with an artificial response.
4. Release the B2 conversation queue normally.
5. Return a controlled failure/result to the caller.
6. Preserve the existing general Discord error UX unless a minimal change is required.

Do not invent a new elaborate user-facing error system.

The exact existing caller behavior should be preserved where practical.

---

# IMPORTANT: USER MESSAGE PERSISTENCE

Inspect the current architecture carefully before deciding whether the user message should be persisted when the model produces no valid response.

Do not automatically persist a user message without its corresponding assistant response if doing so would break the current conversation model.

The preferred behavior is:

```text

        ↓
do not persist a partial conversation exchange
```

unless the existing persistence model makes a different behavior clearly necessary.

Document the decision.

# MALFORMED RESPONSE HANDLING

The B1 Groq reliability layer already provides typed errors.

B3 must ensure that unexpected model response shapes cannot accidentally become:

```text
undefined
null
"..."
```

or another invalid history entry.

Before persistence:

* validate the response
* ensure usable string content
* trim it
* reject invalid content

Do not allow runtime calls such as `.trim()` or `.slice()` to operate on unexpected non-string values without validation.

If malformed output occurs:

* classify it as `malformed_response` where appropriate
* do not persist it
* do not invoke memory extraction with it
* release the B2 queue
* let the existing caller error handling respond safely

# PART 2 — SEPARATE GENERATION FROM PERSISTENCE FAILURE

This is the most important architectural change in B3.

The current flow can effectively behave like:

```text
Groq succeeds
      ↓
SQLite persistence fails
      ↓
generateReply throws
      ↓
caller reports generic AI failure
```

This incorrectly implies that AI generation failed.

B3 must distinguish:

### Generation failure

```text
Groq failed
```

from:

### Persistence failure

```text
Groq succeeded
SQLite failed
```

---

# DESIRED BEHAVIOR

When AI generation succeeds but conversation persistence fails:

```text
Groq succeeds
      ↓
valid response
      ↓
attempt persistence
      ↓
persistence fails
      ↓
DO NOT convert this into an AI-generation failure
```

The generated response should remain available to the caller.

The recommended behavior is:

> Deliver the successful AI response while logging the persistence failure as a degraded conversation-history condition.

However, if the repository's current Discord interaction architecture makes this unsafe, use the smallest safe alternative and document why.

---

# IMPORTANT PERSISTENCE SEMANTICS

Do not silently swallow database errors.

A persistence failure must remain observable.

It should:

* be classified/logged as a persistence failure
* never expose database internals to the Discord user
* never expose SQL, stack traces, paths, or secrets
* not cause a successful AI response to be regenerated
* not cause another Groq request
* not permanently block the B2 queue

---

# CONVERSATION CONSISTENCY

Be careful when delivering a response whose history could not be persisted.

Do not falsely report that the response was saved.

Do not attempt unsafe duplicate writes.

Do not add a complicated recovery queue in B3.

If persistence fails:

* return the generated response according to the chosen degraded behavior
* log the persistence failure
* allow the B2 lock to release
* let the next request reload whatever history was actually persisted

Document the resulting semantics.
