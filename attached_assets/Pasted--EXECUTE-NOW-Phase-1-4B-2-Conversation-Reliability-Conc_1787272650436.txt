# B2 OBJECTIVE

Fix the conversation read-modify-write race condition.

The current problem is conceptually:

```text
Request A → read history
Request B → read same history

Request A → generate → write history A
Request B → generate → write history B

Result:
B can overwrite A's exchange.
```

For the same conversation context, requests must be serialized so the later request sees the earlier request's persisted result.

---

# REQUIRED SCOPE

Serialize by the existing conversation scope:

```text
(userId, guildId)
```

Do NOT create a global AI lock.

These must remain capable of running concurrently:

```text
User A / Guild X
User B / Guild X
User A / Guild Y
```

Only the same conversation context should wait.

---

# IMPLEMENTATION

Use the smallest safe mechanism appropriate for the actual deployment architecture.

If the current bot is a single process, prefer a lightweight in-memory per-conversation async lock/queue.

Requirements:

* Same `(userId, guildId)` requests serialize.
* Different contexts remain concurrent.
* Locks/queues are cleaned up when idle.
* Failed requests release the lock.
* Timeouts release the lock.
* Persistence failures release the lock.
* Unexpected exceptions release the lock.
* No new queue/locking dependency.
* No polling loop.
* No unbounded lock-map growth.

The protected workflow must cover the relevant:

```text
load history
→ build context
→ generate AI response
→ persist history
```

Do NOT merely lock the final database write.

Do NOT hold a SQLite transaction open while waiting for Groq.

---

# RESET

Inspect the existing `/talk reset` behavior and make it deterministic with the new serialization.

A reset must not be followed by an already-running stale request writing old conversation history back over the reset.

Prefer:

```text
existing request completes
→ reset executes
→ conversation is cleared
→ future request sees cleared history
```

If the current architecture requires a different safe implementation, use the smallest correct solution.
