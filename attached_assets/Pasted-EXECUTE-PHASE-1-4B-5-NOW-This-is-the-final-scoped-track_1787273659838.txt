4. USER-FACING ERROR MAPPING
==================================================

Create or centralize a small safe mapping from internal error categories to Discord-facing messages.

The exact existing wording may be preserved where already appropriate, but messages should be useful enough to distinguish major failure classes.

Recommended behavior:

configuration
→ "The AI service isn't configured correctly right now."

rate_limit
→ "The AI service is currently rate-limited. Please try again shortly."

context
→ "That request is too large for the AI context. Try shortening your message or starting a new conversation."

transient_provider
→ "The AI service is temporarily unavailable. Please try again shortly."

network
→ "I couldn't reach the AI service. Please try again shortly."

timeout
→ "The AI request took too long to complete. Please try again."

empty_response
→ "The AI returned an empty response. Please try again."

malformed_response
→ "The AI returned an invalid response. Please try again."

persistence
→ Do NOT expose database details.
→ If the primary AI response was successfully generated, preserve/deliver that response according to B3 behavior.

unknown
→ "Something went wrong while processing your request. Please try again."

The implementation may use slightly different wording if it fits the existing bot tone.

Do not expose:

- HTTP status internals
- stack traces
- SQLite errors
- provider error bodies
- API keys
- request payloads
- prompts
- raw model output

==================================================
5. IMPORTANT B3 RULE
==================================================

A successful AI response must not be thrown away merely because conversation persistence failed.

B3 already establishes:

{
  text: string;
  botName: string;
  personaLabel?: string;
  persisted: boolean;
}

Preserve this behavior.

If:

AI generation succeeds
+
history persistence fails

the caller should still be capable of delivering the generated response.

Do not convert persisted:false into a generic AI failure.

If a user-visible persistence warning is desirable, keep it minimal and avoid exposing database details.

Prefer silent degraded operation unless the existing UX clearly benefits from a warning.
