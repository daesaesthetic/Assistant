You are continuing the Assistant project from the current committed repository state.

The repository is authoritative.

Phase 1.5A context architecture is COMPLETE.

## OBJECTIVE

Harden and complete the Phase 1.5 conversation-context boundary.

The goal is to ensure that every primary conversation request receives a deliberate, bounded, validated context payload while preserving the existing assistant behavior.

The existing `conversation-context.ts` architecture is the foundation for this work.

## EXISTING 1.5A CONTRACT

The current context system provides:

- A 12,000-token planning budget.
- 800 tokens reserved for model output.
- Conservative token estimation.
- Stable assistant instructions.
- Persona context.
- Trait context.
- Memory context.
- Recent conversation history.
- Current user message.
- Explicit truncation metadata.
- Recent-history prioritization.
- Protection against mutating persisted history.

`generateReply()` already uses `buildConversationContext()` before calling Groq.

Preserve these guarantees.

## REQUIRED WORK

First inspect the current Phase 1.5A implementation and tests.

Then harden the context boundary only where necessary.

### 1. Verify the final request budget

Ensure the final message list passed to the primary Groq request is bounded according to the Phase 1.5A contract.

The implementation must account for:

- System/context messages
- Conversation history
- Current user message
- Reserved output tokens

Do not blindly assume the character estimator is exact.

It is an estimate and must remain documented as such.

### 2. Preserve the current user message

Do not silently modify the user's current message merely to satisfy the context budget.

If the current message alone exceeds the planning budget:

- Preserve the current message.
- Remove/reduce lower-priority context first.
- Report the resulting budget condition explicitly.
- Do not mutate persisted history.

Do not invent a new user-message truncation policy unless the repository demonstrates that one is required.

### 3. Make context degradation deterministic

When context must be reduced, use an explicit priority order.

Higher-priority information must survive before lower-priority information.

Preserve the current architectural intent:

1. Current user message
2. Stable assistant instructions
3. Recent conversation history
4. Persona
5. Traits
6. Memories

If the existing implementation uses a different internal allocation strategy, preserve behavior unless a concrete defect requires adjustment.

### 4. Validate the final context

Add a final validation step before the Groq request.

The validator should verify:

- Valid message roles.
- String content.
- Current user message is present.
- No invalid/empty context messages are introduced.
- Estimated input size is reported correctly.
- Reserved output capacity is accounted for.
- Persisted history remains untouched.

Do not duplicate the B3 response validation system.
This is INPUT context validation, not model-output validation.

### 5. Preserve observability without leaking content

If context degradation occurs, make it possible to diagnose through safe metadata.

Do NOT log:

- User messages.
- Assistant responses.
- Memories.
- Persona text.
- Traits.
- Full prompts.

Safe metadata may include:

- Operation.
- Estimated input tokens.
- Reserved output tokens.
- Whether history was truncated.
- Whether optional context was truncated.
- Whether the current message exceeded the planning budget.

Do not introduce verbose logging for normal requests unless necessary.

### 6. Test the boundary

Add focused tests covering:

- Normal context.
- Large history.
- Large persona.
- Large traits.
- Large memories.
- Oversized current message.
- Empty optional sections.
- All optional sections simultaneously.
- Current-message preservation.
- Final budget accounting.
- Context immutability.
- Deterministic degradation order.

Tests must verify actual invariants rather than merely implementation details.
